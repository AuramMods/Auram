# Changelists: launcher integration guide

Auram publishes a small JSON delta with each release so a launcher can update
only the files that need to change. A delta lists repository paths; the actual
file contents still come from Git or HTTP at a particular release commit.

This document describes the format generated by [`scripts/release.py`](../scripts/release.py),
then recommends a launcher implementation. The producer and its integration
tests exist in this repository. Download planning, caching, file ownership,
transactions, repair, and installation policies described here are work for the
launcher; producing a changelist does not implement those features by itself.

## 1. Release identity and discovery

The repository is `https://github.com/AuramMods/Auram.git`. Its release metadata
is the root `auram.json`:

```json
{
  "version": 145,
  "changelist": "changelist/145.json"
}
```

- `version` is a JSON integer for releases produced by the current script.
  It equals the total number of commits reachable from the release commit,
  including the release commit itself. It is a build number, not a semantic
  version or a count of releases. Builds can skip numbers: `139`, `141`, `143`,
  and `145` are successive releases in the current history.
- The release tag is the decimal string of that number, such as `145`.
- `changelist` is a repository-relative path to the manifest for that release.
  Read this field instead of assuming a filename.
- Other metadata fields can exist and are preserved by the release script.
- Older tags such as `1.0.7` remain valid release identities and delta bases.
  Store version identities as strings internally when comparing them to tag
  names. Do not parse legacy tags as integers or assume `version - 1` exists.

A launcher can use `auram.json` on `main` as a discovery hint. Resolve its
version tag to a commit, then read `auram.json` again at that commit and use
that pinned snapshot for the entire update. `main` can contain unreleased
commits while still advertising the last released version. Never download the
payload from moving `main` after discovering a release.

The script publishes Git tags, not GitHub Release objects or release assets.
A launcher must not require a corresponding entry from GitHub's Releases API.
If discovering tags directly, select the intended release history/channel;
sorting all repository tags lexicographically is insufficient. There is no
channel field in schema 1.

Record both the installed version/tag and its resolved **commit ID**. The commit
is the precise baseline. A matching version label alone cannot prove that the
installed files came from the same snapshot.

## 2. Schema 1

This is the actual manifest for build 145:

```json
{
  "schema": 1,
  "version": 145,
  "previousVersion": "143",
  "previousCommit": "5d9029c5a91db65aa71f0b63c8a7dd3698c0fc81",
  "contentCommit": "d0158876b10d7e4ac3132974fcb82f796a753b4f",
  "changes": [
    "*auram.json",
    "+changelist/145.json",
    "-minecraft/mods/Auram.jar",
    "+minecraft/mods/AuramCore-1.0.5.jar",
    "+minecraft/mods/Imperium-1.0.0.jar",
    "-minecraft/mods/Imperium.jar",
    "+minecraft/mods/Satiscraftory-1.0.0.jar",
    "-minecraft/mods/Satiscraftory.jar"
  ]
}
```

| Field | Meaning for a launcher |
| --- | --- |
| `schema` | Format version. This document defines integer `1`. Use a supported tree-based fallback or report an unsupported format for other values. |
| `version` | Target build number; it must agree with the pinned release's `auram.json`. |
| `previousVersion` | Exact tag name of the base release, as a string; `null` if no earlier release tag exists. |
| `previousCommit` | Base release's peeled commit ID; `null` together with `previousVersion` for the first release. |
| `contentCommit` | Committed pack snapshot immediately before the release metadata commit. This is provenance, not the final download revision. |
| `changes` | Array of operation-prefixed repository paths. |

The target release commit ID is **not a manifest field**. Obtain it by resolving
the release tag and retain it alongside the manifest. For build 145 that commit
is `73c6252eb99a6d8cd502e2cdca33f1a06179ce15`.

### Operations and paths

| Prefix | Meaning in the producer's diff | Installation action |
| --- | --- | --- |
| `+` | Path added since the base release | Install the complete target file. |
| `*` | Path modified, including a Git file-type change | Replace with the complete target entry. |
| `-` | Path removed since the base release | Remove the previously managed entry. No download. |

For applying a composed plan, `+` and `*` are both an **upsert**: make the managed
path match the target snapshot. Their distinction describes release history;
it is not a reason to fail an otherwise valid resumed download. An unexpected
user-owned file at the destination still needs the launcher's collision policy.

Parse each JSON string as `operation = entry[0]` and `path = entry[1:]`.
Do not split on whitespace, strip the path, expand globs, or interpret a leading
`*` as a wildcard. Paths are relative to the **repository root**, use `/`, and
can contain spaces, tabs, Unicode, or escaped newlines. The generator uses
NUL-delimited Git output to preserve these names. Entries are sorted by path,
with one operation per path in a manifest. Array order is not execution order.

### What a delta covers

Each manifest is the **net tree difference** between the previous release and
the target release, rather than a log of every intervening commit:

- Binary files such as jars and resource-pack zips are included.
- Changes reverted before that release do not appear.
- Renames are always represented as deletion plus addition; there is no rename
  operation or old-to-new pairing. The build 145 example demonstrates this.
- Directories are implicit. Empty directories are not tracked by Git.
- `auram.json` and the new manifest's own path are explicitly included. They
  exist at the final tagged release commit, even though they can be absent or
  outdated at `contentCommit`. Fetch files from the final release commit.
- If there is no earlier tag, the base is an empty tree and every tracked path
  is an addition. This does not make every later manifest a complete inventory.
- The diff covers **all tracked repository paths**. It does not apply
  `.packignore`, client/server exclusions, or a launcher installation filter.
  `.gitignore` prevents untracked runtime data from being added normally; it
  does not exclude already tracked files from a release diff.

Schema 1 supplies paths and operations only. It has no file sizes, blob IDs,
checksums, binary patches, executable bits, symlink targets, platform/side
classification, or minimum launcher version. Obtain additional information
from the pinned Git tree when needed. Changed jars require their complete new
contents unless the transport or a separate cache provides reuse.

## 3. Applying one release

If the installation baseline is exactly build 143's commit, the build 145
manifest is sufficient to plan that update:

1. Pin tag `145` to its commit and read its metadata and manifest there.
2. Confirm that `previousCommit` equals the installed baseline commit.
3. Select the paths managed by this launcher/profile and map them to destinations.
4. Stage the added/changed files from the pinned target commit.
5. Apply replacements and deletions as one recoverable update while the game
   is stopped. In particular, remove old mod filenames before allowing launch.
6. Record the target commit, version, and updated ownership inventory only after
   the complete update succeeds.

An unchanged path is left alone by this fast path. Therefore a delta does not
repair an unrelated missing or corrupted file, and a version check alone does
not prove installation integrity. Provide a separate repair operation.

## 4. Skipping releases without downloading intermediate files

A target manifest covers its immediate base, not every older installation.
For example, updating `139 -> 145` needs the chain:

```text
145 manifest: previousVersion 143, previousCommit = commit of 143
143 manifest: previousVersion 141, previousCommit = commit of 141
141 manifest: previousVersion 139, previousCommit = commit of 139
installed baseline: commit of 139
```

Walk backward from the pinned target. At each step, resolve the previous tag,
verify its commit agrees with `previousCommit`, and read that snapshot's
`auram.json.changelist` if another manifest is needed. Stop as soon as the base
commit equals the installed commit. Do not require a manifest at the installed
baseline: build 139 can directly update an installation of legacy tag `1.0.7`,
because its `previousCommit` identifies that exact baseline.

Detect cycles, inconsistent identities, and a chain that never reaches the
installed commit. If a required manifest is missing or the baseline predates
the chain, use the tree fallback in section 8. Do not apply the newest delta
alone and mark the installation current.

### Compose the chain into one final plan

The newest operation for each path determines its final state. Walk manifests
**newest to oldest** and keep the first occurrence of each path:

```text
plan = {}  # repository path -> operation
for manifest in chain_newest_to_oldest:
    for entry in manifest.changes:
        operation, path = parse_and_validate(entry)
        if path not in plan:
            plan[path] = operation

for path, operation in plan:
    if not installation_policy.manages(path):
        continue
    if operation == '-':
        schedule_managed_deletion(path)
    else:
        schedule_upsert(path, source_commit=TARGET_RELEASE_COMMIT)
```

Establish the complete, valid chain before applying this plan. Validate each
manifest before coalescing; repeated paths across different releases are normal.
Apply destination policy and ownership checks to both upserts and deletions.

| Changes from oldest to newest | Final action |
| --- | --- |
| Add A, modify A twice | Fetch A once from the final target. |
| Add A, delete A | No download; remove A only if the installation owns it. |
| Delete A, add A again | Install A from the final target. |
| Modify A, revert A in a later release | Ensure A matches the final target; a blob comparison may avoid downloading it. |
| Rename old.jar to new.jar | Delete old.jar and install new.jar. |
| Rename A to B, then B to C | Install C; remove owned A/B. Never fetch B. |

Do not concatenate operations and execute them in JSON order. Do not download
each intermediate version of a large jar. The complete chain is needed for
planning, but every final upsert can use the **same pinned target commit**.

## 5. Installation scope and file ownership

Repository paths and installation paths are different namespaces. Define an
explicit profile mapping. For example:

| Repository path | Possible launcher handling |
| --- | --- |
| `minecraft/mods/example.jar` | `<game directory>/mods/example.jar` |
| `minecraft/config/example.toml` | `<game directory>/config/example.toml`, using the launcher's config policy |
| `minecraft/kubejs/**`, `minecraft/scripts/**`, resource packs | Corresponding game-directory paths |
| `auram.json`, `changelist/**` | Launcher metadata/cache; need not be copied into the game directory |
| `mmc-pack.json`, `instance.cfg`, icons | Instance metadata if that launcher uses them |
| `docs/**`, `tests/**`, `scripts/release.py`, development tools | Usually excluded from the playable installation |
| `server_files/**` | Dedicated-server template inputs, requiring a separate destination policy |

This table suggests policies; it is not a machine-readable installation
specification supplied by the manifest. `.packignore` is an existing packaging
input, and `server_config.conf` describes ServerPackCreator inputs/exclusions.
The release script does not interpret either file. A server updater must also
apply its client-only mod rules and server mappings; changelists alone do not
produce a server pack or install Forge/Java.

Keep a launcher-owned inventory containing repository paths, mapped destination
paths, and installed/base content identities. Store it outside the distributed
pack files. Track the profile/filter version as well. If the filter or mapping
changes, reconcile against a complete target inventory: previously excluded
files will not necessarily appear in the next delta.

Use separate treatment for pack-managed files, preserved local data, and user
overrides. Saves, screenshots, logs, and user-added mods must not be wiped just
because they are absent from a manifest or target tree. A deletion should remove
an owned path, not recursively delete its parent directory. A missing deletion
target is already satisfied and should not fail a resumed update.

For tracked configs/options that users can edit, choose and document a policy:
replace with the pack version, retain an explicit override, or compare against
the last distributed content and preserve/back up conflicts. If retaining an
override, keep it separate in state so the release baseline does not imply
that the disk bytes match the distribution. Do not silently merge arbitrary
binary files or keep both old and new versions of a managed mod jar.

Validate the actual mapped destinations: reject absolute paths, parent traversal,
escape through existing symlinks, and platform-invalid names. Detect collisions
after mapping, including case-insensitive filesystems. A filename valid in Git
can still be unsupported on the destination platform. Handle such failures
explicitly instead of writing outside the instance or overwriting another file.

## 6. Retrieving files efficiently

### HTTP without a Git checkout

Once a release is pinned, individual files can be read using:

```text
https://raw.githubusercontent.com/AuramMods/Auram/<RELEASE_COMMIT>/auram.json
https://raw.githubusercontent.com/AuramMods/Auram/<RELEASE_COMMIT>/changelist/145.json
https://raw.githubusercontent.com/AuramMods/Auram/<RELEASE_COMMIT>/minecraft/mods/AuramCore-1.0.5.jar
```

Replace `<RELEASE_COMMIT>` with the resolved commit ID. URL-encode individual
path segments, preserving `/` separators; do not concatenate unescaped spaces,
`#`, `?`, or control characters into URLs. Stream binary bodies to staging files.
An HTTP error page is not valid jar content. A download 404 is an update failure,
not an implicit deletion; deletions come from the plan or a complete tree diff.

For tag resolution, GitHub's
[`GET /repos/{owner}/{repo}/git/ref/tags/{tag}`](https://docs.github.com/en/rest/git/refs#get-a-reference)
returns an object type and ID. Current release tags are annotated, so the first
object ID can be a **tag object**, not a commit. Follow tag objects with
[`GET /repos/{owner}/{repo}/git/tags/{tag_sha}`](https://docs.github.com/en/rest/git/tags#get-a-tag)
until the object is a commit. Also support lightweight legacy tags that already
point to commits. With Git, peel using `git rev-parse 'refs/tags/145^{commit}'`.

Cache metadata by `(repository, commit, path)` and file bodies by content identity
when available. Recheck discovery using HTTP cache validators where supported;
commit-pinned responses can be reused for that identity. Bound concurrency and
retry transient network/rate-limit failures with backoff. Avoid one API metadata
request per jar when one tree response can supply the required entries.

### Git object cache / partial clone

A dedicated launcher cache can retain Git objects across updates without
checking out the full pack. An initial cache can be created with:

```sh
git clone --filter=blob:none --no-checkout --single-branch --branch main \
  https://github.com/AuramMods/Auram.git auram-cache
```

Partial clone's `blob:none` defers file contents until needed; `--no-checkout`
avoids materializing the pack during creation. This still transfers commit/tree
metadata. It requires server support, so handle an unsupported filter or less
efficient transfer. See the [Git clone documentation](https://git-scm.com/docs/git-clone).

Fetch the chosen tag explicitly, resolve it, and read only needed metadata or
blobs. For example, with `git -C auram-cache` as the command prefix:

```sh
git -C auram-cache fetch --no-tags --filter=blob:none origin \
  refs/tags/145:refs/tags/145
git -C auram-cache rev-parse 'refs/tags/145^{commit}'
```

Once the commit is known, `git show <commit>:<path>` can read an exact file.
For many files, resolve paths to blob IDs from the tree and use
[`git cat-file --batch`](https://git-scm.com/docs/git-cat-file) to avoid starting
one process per file. Parse its size-framed binary output correctly. Pass
arguments/stdin directly through the process API; do not construct shell commands
from manifest paths. Preserve Git blob bytes for consistent hashes, rather than
applying local line-ending conversions.

A batched local read does not guarantee one batched network request: missing
promised blobs can trigger lazy fetches. Measure that behavior in the chosen Git
client and transport. Reuse the persistent object cache, and avoid checking out
an entire directory merely to retrieve a few changed files.

Sparse checkout controls which paths appear in a working directory; it does not
by itself prevent downloading all historical file contents. Combine it with
partial clone when a checkout is useful. Cone mode selects directories and can
include extra ancestor files; arbitrary individual-file selection needs different
handling. For a delta cache, direct object reads avoid checkout pattern management
and avoid treating the live game directory as a disposable sparse worktree.
See the [Git sparse-checkout documentation](https://git-scm.com/docs/git-sparse-checkout).

The launcher can use shallow history, explicit tags, or tree access as appropriate
for its transport. It does not need the complete commit history to apply a verified
manifest chain. The **publisher** needs full history to calculate build numbers;
that requirement does not apply to a launcher.

### Content reuse and download accounting

The most efficient plan downloads each distinct final blob at most once. If a
file at a new path has the same blob ID as a cached/local managed file, reuse
verified bytes. The three build 145 jar renames changed no contents, so a cache
with tree/blob identities can perform them without downloading jar bodies.
The manifest alone cannot establish that identity or pair the renamed paths.

Tree metadata also allows the launcher to discard a composed upsert whose final
blob/mode already matches the installed base, or a deletion for a path the base
never owned. Reuse requires content identity, not matching filenames or versions.
Hash the bytes if local edits are possible. Schema 1 has no size information for
an exact byte progress total; obtain sizes from a tree/transport or show counts
until sizes are available. There is no application-level binary delta protocol.

## 7. Interruptions, verification, and activation

Keep updating separate from running the game. Use an instance update lock and
prevent launch until activation or rollback completes. Download and verify the
whole plan before removing the currently installed files.

Persist a transaction journal containing the old baseline, pinned target commit,
plan, staged blobs, completed file operations, and backups needed for rollback.
Install through a staging directory/generation switch or a recoverable sequence
of per-file replacements. A per-file atomic rename does not make a multi-file
pack update atomic. Resolve file-to-directory and directory-to-file transitions
in dependency order; do not recursively delete unrelated user files to make room.

Upserts and deletion of already absent owned files should be repeatable. On
restart, finish the same pinned transaction or restore the old installation.
Do not discover a newer release halfway through and mix its files into the
transaction. Space for staging/backups and file locks, particularly on Windows,
are operational concerns for the launcher to handle.

Only after successful activation should the launcher atomically save the new
baseline/version/ownership state. A downloaded `auram.json` is release metadata,
not proof that installation completed. Do not use replacing that file as the
commit point for an otherwise unfinished update.

For verification, Git tree blob IDs can identify expected content. In this
SHA-1 repository a blob ID is `SHA1("blob " + decimal_byte_length + NUL + bytes)`,
not the plain SHA-1 of the file. Store a separate SHA-256 if useful for a local
cache, but schema 1 does not publish SHA-256 values. Size checks alone cannot
detect same-size corruption. Commit pinning and content checks give consistency;
the script does not sign tags or provide a separate signature-verification
protocol. The launcher still trusts its configured repository and transport.

## 8. Fresh installs, old baselines, repair, and rollback

Use a complete target Git tree when there is no trustworthy installed baseline,
a required manifest is unavailable, a chain branches away from the installed
commit, the installation policy changes, or the user requests repair/rollback.

| Situation | Plan |
| --- | --- |
| Fresh install | Enumerate the target tree, filter/map it, and install all selected entries. |
| Legacy install with known commit | Compare the installed/base tree to the target, or use a chain that reaches that exact commit. |
| Install with unknown history | Enumerate the target; reconcile conservatively using known ownership and local conflict policy. |
| Repair | Compare selected target entries with actual managed disk contents, including paths absent from recent deltas. |
| Downgrade or divergent history | Compute an explicit base-to-target tree difference. Forward changelists cannot simply be run backward. |

An already-current version can still require repair. A target tree is also often
cheaper than many requests for a very long manifest chain. Choose based on
available cache/history and metadata cost; both methods should produce the same
target snapshot under the same installation policy.

With Git, enumerate via `git ls-tree -r -z <target-commit>` and compare available
snapshots via `git diff --name-status --no-renames -z <base> <target>`. Parse NUL
delimiters and Git modes; ordinary regular files, executable files, symlinks,
and submodules need explicit support or a clear unsupported-entry error.

Over HTTP, GitHub's [Git Trees API](https://docs.github.com/en/rest/git/trees#get-a-tree)
can enumerate paths, blob IDs, sizes, and modes. Resolve the commit's tree and
request it recursively. If the response has `truncated: true`, walk non-recursive
subtrees until the inventory is complete. A truncated response must never be
treated as an authoritative list of absent/deleted files.

For reconciliation, install missing/different selected target files and remove
only previously owned paths absent from the selected target. Keep user data and
overrides according to policy. Cache the resulting inventory so later releases
can return to the small-delta fast path.

## 9. How publication creates this contract

The maintainer first commits the payload changes, then runs:

```sh
python3 scripts/release.py
```

The script:

1. Fetches tags from the selected remote, unshallowing history when necessary.
2. Selects the closest reachable release tag using Git describe among names
   matching `v?` plus one to three numeric components. It does not choose the
   numerically largest tag from an unrelated branch.
3. Calculates the net committed-tree diff with rename detection disabled.
4. Sets the build number to the reachable commit count plus one for the upcoming
   release commit; writes `auram.json` and `changelist/<build>.json`.
5. Commits only those two metadata files and creates an annotated numeric tag.
6. Pushes the tagged commit to the current branch and the tag together using
   `git push --atomic`, without force. A rejected atomic push publishes neither ref.

Uncommitted payload changes are not released. Build numbers assume the maintained
history; they are not globally unique across arbitrary divergent histories.
Treat published tags as stable release identities and use the resolved commit
to detect an unexpected retargeting.

`--dry-run` previews a plan from local committed history without fetching,
writing files, creating commits/tags, or pushing. `--remote <name>` selects a
different remote. After a publication failure, local metadata/commit/tag remain;
`--push-only` retries the version recorded in `HEAD:auram.json` and pushes the
existing tag's commit, rather than generating another release. A publication
retry does not require any special launcher behavior: consume the complete
release once available.

## 10. Launcher acceptance scenarios

Before shipping an implementation, exercise these observable outcomes:

- A one-release update downloads only selected added/changed final files and
  removes selected obsolete managed files.
- A skipped-release update handles repeated edits, create/delete, delete/recreate,
  reverted content, and chained renames without downloading intermediate jars.
- The build 145 rename update removes all three old filenames; a verified blob
  cache can reuse their bytes for the versioned filenames.
- Legacy tag `1.0.7` can use build 139's delta when its commit matches the baseline;
  an older or unknown installation takes the complete-tree path.
- Discovery moving during a download does not change the pinned target.
- A failed download, invalid body/hash, interrupted replacement, or locked file
  does not record the target as installed or permit launch with mixed mod versions.
- Resuming repeats safe operations or rolls back cleanly, preserving user data.
- Spaces/Unicode survive parsing and retrieval; unsupported destination names,
  traversal, symlink escapes, and mapped-path collisions are handled explicitly.
- A missing manifest or truncated tree response cannot cause an incomplete
  installation to be recorded as current.
- A changed installation filter and a repair request reconcile the complete
  selected target, including files untouched by recent releases.

The producer's existing tests are in [`tests/test_release.py`](../tests/test_release.py).
They cover net deltas, binaries/unusual paths, rename representation, reverted
changes, legacy/numeric bases, a first release, local uncommitted work, shallow
publisher history, and atomic-push rejection/retry. Run them with:

```sh
python3 -B -m unittest discover -s tests -v
```

Those tests validate publication behavior. They do not substitute for the
launcher's own download, filesystem, recovery, and installation-policy tests.
